# Hermes 是否适合作为个人 AI PM Studio 的基础

核查日期：2026-10-23。范围：个人自用、持续迭代的 Agent 工作流，
不接公司业务系统。本次判断依据固定版本代码和执行链路测试，
不是 README 功能清单，也不是生产可用性认证。

## 当前判断

**值得作为个人通用 Agent 运行环境试用；暂不值得重度改造为自己的框架。**
Hermes 已具备需要的大部分底层能力。真正待验证的是：分角色分析能否稳定
减少遗漏与人工返工，是否值得增加的调用成本和维护负担。

本次新增一个可运行示例，保留单 Agent 基线。应先用真实想法完成比较，
再决定是否投入长期记忆、后台自动化和界面。技术跑通不等于多 Agent 有价值。

## 关键能力：已有、变化与缺口

以下文件均指本仓库路径；上游变化指上表固定 main SHA，非全部 release 历史。

| 能力 | 分叉中的实际实现 | 上游关键变化 | Studio 决策 |
|---|---|---|---|
| Agent 调度 | `run_agent.py::AIAgent.run_conversation` 负责调用、工具循环、重试、压缩；子代理各有迭代预算 | 核心循环拆到 `agent/conversation_loop.py` 等模块，预算与上下文管理继续拆分 | 直接复用，不改循环；另加确定性的业务阶段编排 |
| 子代理 | `tools/delegate_tool.py` 支持同步单任务/批量并行；独立会话、task_id、受限工具、状态/耗时/token 返回；父任务中断传递给子任务 | 拆为 `delegate_tool_*`；新增 background、output_schema、list/steer/stop 与按模型或 profile 路由；角色权限变为按深度推导 | 当前原型用同步批量和 leaf；升级后重新验证适配层，不能原样照搬参数 |
| 工具继承 | 旧 `_build_child_agent` 支持请求工具集与父工具集交集；leaf 禁用 memory/发送消息/递归委派等 | 新建子代理主要继承父能力；`role` 为兼容字段，旧顶层 toolsets 参数不在同一签名中 | 原型所有角色均禁用外部工具，实际 HTTP 请求验证未暴露工具 |
| 完成判断 | 旧 `_run_single_child` 只要有非空 summary 就可能标为 completed，同时用 exit_reason 标记迭代耗尽 | 新实现增加结构化完成状态与输出 schema 校验 | 必须同时检查 status 与 exit_reason；本例另做 JSON/引用校验 |
| Skills | `tools/skills_tool.py` 从 profile 的 skills 目录加载 SKILL.md/参考文件；`agent/skill_commands.py` 支持命令入口 | 动态解析 profile 路径、增加候选来源/冲突处理及索引相关代码 | 直接复用角色 Skill，编排不依赖模型是否记得加载它 |
| 长期记忆 | `tools/memory_tool.py` 的 MEMORY.md/USER.md 为有容量限制的长期摘要；会话启动冻结快照；`hermes_state.py` 是 SQLite 会话历史；另有 memory provider 插件 | `memory_tool_store.py` 增加原子批处理等；provider 明确 profile/会话范围及 on_delegation 等接口 | 能复用存储和检索；还需项目范围、来源、人工确认、过期更新策略，不把历史日志当事实库 |
| 工具调用 | `model_tools.py`、`tools/registry.py` 管理工具注册、发现、schema、调用；MCP 与插件扩展已存在 | 注册表增加更细的会话 scope、锁和插件覆盖策略，MCP 相关实现进一步拆分 | 后续按角色加最小工具集，优先插件/MCP，避免给所有角色完整权限 |
| 持久任务 | `cron/jobs.py`/`scheduler.py` 已支持定时任务；`hermes_cli/kanban_db.py` 已有 SQLite 任务依赖、认领和事务 | Kanban 拆出 workflow/dispatch/graph 等模块；Cron 继续扩展 | 定时与可靠队列不是本次新增需求；真正需要跨会话运行时再接已有机制 |

几个容易误判的边界：

1. 子代理的上下文隔离，不代表文件系统、网络或权限的强隔离。
2. 旧分叉的 `skip_memory=True` 意味着子代理不会自动继承长期记忆。
   需要父级明确选择并传入相关内容；“都有记忆能力”不等于“共享同一项目知识”。
3. 同模型的不同角色可能重复同一个错误。校验代理可以检查证据与一致性，
   不能凭角色名称获得独立事实来源。
4. Cron/Kanban 的存在不能证明它们与本例已经稳定集成。本例未接入这两项。

## 本次实现

新增文件集中在 `examples/ai_pm_studio/` 和 `tests/test_ai_pm_studio.py`，
不修改 Agent、委派、记忆或工具核心。

- 输入：个人产品想法、约束、带 ID 的证据。
- 第一阶段：critic 与 designer 使用独立上下文并行执行。
- 第二阶段：verifier 获得原始输入及两份完整结果，逐条检查主张。
- 输出：结构化结果、完整交接记录、耗时/token、最终决策与下一次实验。
- 基线：同输入、同模型、同工具权限，用一个角色完成分析、设计与自检。

`studio.py::HermesBackend` 是唯一依赖 Hermes 运行接口的适配层。
`run_workflow` 负责阶段顺序和失败处理；角色 Skill 可以单独迭代。
这样将来换运行框架时，输入协议、角色内容、校验规则和评测方法仍可保留。

本轮没有做：联网资料调查、自动永久记忆写入、跨会话恢复、定时运行、
角色间无限讨论、多模型路由或前端界面。这些不是验证最初价值所必需的。

## 用什么判断值不值得继续

建议用 5–10 个真实个人想法做方向性试用，不把小样本当统计结论。
例如阅读收件箱、个人周复盘、资料整理自动化；不要用公司场景替代自用需求。

对每个想法保留同一份 brief，分别跑 single/multi，交错顺序，隐藏模式标签后
人工评价；不要将一个模式生成的内容补到另一个的输入。

| 观察项 | 记录方法 |
|---|---|
| 关键遗漏 | 是否遗漏会改变“做/不做”的约束或风险；由人判断 |
| 无依据断言 | 是否把假设写成事实、曲解原文或虚构来源 |
| 可行动性 | 能否直接执行一个足够小的验证动作 |
| 总成本 | API 用量/账单、等待时间、人工检查与修改时间 |
| 持续采用 | 一周后是否自发再次使用，而非只为测试点击 |

建议继续条件：多 Agent 在多个任务上减少关键遗漏或人工返工，且新增成本
自己愿意承担。若收益主要只是“更长、更像多人讨论”，保留单 Agent + Skills。
若失败主要来自材料不足，先改输入与证据采集，不增加 Agent 数量。
在没有真实模型试用前，这些只是待验证的决策条件，不是已达到的指标。

## 与自行搭建轻量 Harness 比较

这里的 Harness 指模型外的工具、状态、权限、执行与评测机制组合，
不是已经被验证的另一款现成框架；Hermes 本身也包含这类机制。

| 维度 | Hermes + 薄业务层 | 自建轻量 Harness |
|---|---|---|
| 立即可用性 | CLI、模型协议、Skills、工具、会话、记忆和任务已有基础 | 只做这个三角色文本流程很直接；完整个人助手能力仍需逐项补 |
| 开发复杂度 | 业务层小，但需理解 Hermes 配置、工具继承和内部 API | 固定流程更透明；逐步加入工具、重试、压缩、调度后复杂度上升 |
| 维护成本 | 共享上游修复，但这次约五个月差距已产生明显接口漂移 | 依赖面较小、节奏自控；模型协议与可靠性问题由自己负责 |
| 扩展空间 | 快速连接现有工具、消息入口、任务队列和记忆后端 | 数据和流程自由度高，更适合形成自己的独特产品架构 |
| 本例适配度 | 已能运行，但完整框架明显大于三个文本角色所需 | 若最终只保留少数固定流程，更可能是合适的长期方案 |

**建议路径：**保留本 PR 作为固定版本上的实验，不在旧 main 上不断堆功能。
真实试用有收益后，再单独做稳定上游版本同步与适配测试，避免把大规模升级
和业务原型混在同一个 PR。若主要价值收敛为少数固定文本流程，或每次扩展都
要修改 Hermes 内核，则把现有角色协议与评测迁移到轻量 Harness。

如果目标仍是广泛探索 Skills、工具、记忆和自动化，先复用 Hermes 的理由
较强；如果目标转为开发一款具有自己数据模型和流程产品形态的工作台，
自行搭建的理由会增强。两者之间应由真实使用和维护成本决定。
